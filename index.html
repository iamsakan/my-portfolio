Local RAG assistant over internal documentation 01
docs + task DB → LlamaIndex / Qdrant (hybrid) → Ollama (local LLM) → chat / CLI

Problem

Colleagues needed to search internal documentation and past task history, but the material is sensitive enough that routing it through an external API wasn't an option.

What I built

A retrieval-augmented chatbot running entirely on local infrastructure: LlamaIndex over a Qdrant vector store with hybrid dense + sparse retrieval (bge-m3 embeddings plus BM25), served by a local Ollama model. A dual-mode retriever blends document search with a guarded natural-language-to-SQL agent over a MySQL task database, so the same interface answers "what does the policy say" and "what's the status of this task."

Why it matters

Ingestion handles PDF, DOCX, PPTX, CSV, and XLSX, plus OCR for scanned Slovenian, Croatian, and Serbian documents, with incremental indexing and checkpointing so re-runs don't start from zero. Nothing leaves the building.

QuizArena — a public quiz platform 02
author quizzes → public browsing → solve & score → rate once → leaderboard

Problem

Ad-hoc quizzes are easy to write and hard to trust — there's no way to tell a well-made one from a rushed one before you've already spent time on it, and no easy way to see whether you're actually improving across repeated attempts.

What I built

A web app for creating, browsing, and solving quizzes, with results tracked per user so people can watch their own progress over time. Every quiz can be rated once after solving, so quizzes can be sorted by rating instead of just recency — a much better signal for someone deciding what to try next. A leaderboard adds a bit of competitive motivation on top.

Why it matters

It turns quiz-taking into something with a feedback loop on both sides — progress tracking for the person answering, and a quality signal (via ratings) for whoever wrote the quiz.

Order acknowledgement parser 03
order PDF → parsed BOM (flat + nested) → validated Excel (totals + checks)

Problem

Lab equipment order acknowledgements arrive as PDFs with flat or deeply nested bill-of-materials structures, and turning them into something finance and fulfillment can actually work with used to be a manual copy-paste job.

What I built

A Python script that parses both BOM structures and exports a structured Excel file — colour-coded rows, formula-based totals, and a validation pass that flags rows that don't add up — after I'd done the conversion by hand once to know exactly which edge cases mattered.

Why it matters

It replaced a recurring, error-prone manual task with something that runs the same way every time, in a workflow conducted mostly in Slovenian.

How I work

A few things true across most of these projects

Local-first

If a task doesn't need the cloud, it doesn't get the cloud. Internal documents and task data stay on infrastructure I control, indexed and queried by models running locally.

Built for real people

A project isn't done when the code runs — it's done when someone's actually using it. Coworkers search documentation through the RAG chatbot, a farmer logs flock records in FlockBook, people solve and rate quizzes on QuizArena. That's the bar, not a repo that only runs on a laptop.

Don't trust free text

Language models draft well and promise structure badly. I constrain outputs with schemas, validate them against the source, and keep a guarded path — like read-only SQL — between a model and anything that matters.

Automate after, not instead of

Most of my tools started as a task I did by hand at least once. That manual pass is what tells you which edge cases actually matter before you build the wrong automation.
